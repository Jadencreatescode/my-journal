# Weekly and monthly learning review

## Purpose and boundary

Turn validated daily records into a small set of useful improvements, rather than a growing inventory of redundant skills and memories. Use this procedure only for an explicitly requested interactive review or its separately approved implementation pass. The default is recommendations only: no automatic scheduling, memory mutation, tool installation, or recovery work. This procedure does not expand the unattended daily generator's tools or permissions.

## Review procedure

1. Resolve the exact date window and journal timezone. State whether weeks mean calendar weeks or consecutive blocks. A final partial week stays visibly partial.
2. Use `journal_status` and read-only `journal_plan_backfill` for inventory and gaps, then `journal_read_entries` for validated evidence. Inventory alone is not validation. Retry dates rejected solely for output budget individually. Never bypass evidence rejection by reading an uncertified note as certified evidence. Report any remaining rejected dates and errors.
3. Maintain a bounded date register, using an approved private working location if a file is needed. Calculate unique validated dates, missing dates, rejected dates, and recommendation totals programmatically. A missing entry is not an inactive day. Profile and platform coverage is not a census of every machine. Do not widen the authorized source scope.
4. Extract candidates from decisions, corrections, completed and verified work, failures, and repeated friction. Distinguish discussed ideas, decisions, attempts, completed work, verified demonstrations, and currently available capabilities. Cite the source date and section for each candidate. A historical success is not current readiness or general qualification.
5. Before proposing changes, compare each candidate with the actual relevant skill sections, current canonical project records, and scoped memory retrieval where authorized and available. Read more than titles. Prefer reinforcement or a narrow correction when guidance already exists. A failed semantic query is a bounded retrieval miss, not proof of absence; check the authoritative record. If a destination or retrieval tool is unavailable, report the comparison as incomplete rather than inventing a gap.
6. Preserve project scope, explicit approval boundaries, and the latest applicable decision. A choice or exception within one project or stage must not become a universal rule. Keep the original date convention; UTC and journal local dates may differ. Do not silently rewrite chronology to make dates match.
7. Classify each candidate as **Reinforce**, **Reconcile**, **Capture**, **Retrieval repair**, **Reuse**, or **Investigate**. Reinforce existing guidance; reconcile conflicts; capture genuinely missing lessons; repair retrieval of existing records; consider demonstrated capabilities for reuse; investigate uncertain findings. Reuse means considering an existing demonstrated route, not activating it. Only propose external skill discovery when a real gap remains after inspecting the installed library.
8. For every recommendation record: dated evidence and section, evidence state, existing guidance, specific gap, intended change, authoritative destination, expected benefit, authority or cost boundary, and future verification test. A proposal to add a tool must identify installation, model, privacy, exposure, and spending implications. Name destinations explicitly without placing private paths or identifiers in public documentation.
9. Rank the smallest useful set. Report uncertainty and limited coverage. A retrospective comparison with today's skills does not prove those skills were absent in the historical week or that the review improves outcomes causally.

## Approved implementation pass

1. Resolve approval from the active conversation and its exact proposal. A simulation or recommendation request authorizes no mutations. General approval of a correction pass does not authorize new schedules, spending, deployments, cleanup, or unrelated repairs. Never change memory automatically as a consequence of a review.
2. Recheck each live destination immediately before editing. Other conversations may already have captured a finding. Preserve concurrent legitimate changes and use expected content or revision checks for external updates.
3. Back up existing instructions and records through the user's established backup route before changes that require recovery. Never create a new backup destination or silently substitute a mirror for authority. If the required recovery route is unavailable, stop that edit and report the blocker.
4. Correct existing skills in place where possible. Put reusable procedures in the relevant skill, exact project choices in canonical project records, contextual facts in an approved semantic memory destination, and only universal constraints in standing prompt memory. Do not add standing memory solely because space exists or a review produced a candidate. Every mutation must remain inside the approved scope.
5. Verify canonical writes by exact readback before any projection. If an approved sanitized mirror or index exists, use its established route; do not create one implicitly. Check natural language retrieval where supported and distinguish saved, indexed, retrievable, and pending propagation. Do not duplicate retention repeatedly to compensate for asynchronous indexing.
6. Verify skill loading and relevant acceptance scenarios. Instruction edits do not repair a generator, certify an artifact, retrain a model, or prove future compliance. Keep policy checks separate from runtime checks.
7. Record a separately dated implementation receipt in the approved private destination beside the canonical review, including unchanged findings, applied edits, evidence, verification results, pending work, and any authority gate. Preserve the original recommendation or simulation rather than rewriting it as if actions had already happened.

## Missing dates and recurring failures

Use the existing metadata workload check, where authorized, to distinguish no source activity from unfinished synthesis. Inspect the existing controller, frozen bindings, exact run date, completion receipts, and digest progress before proposing repair. A daily job can finish an older frozen date while skipping the expected date; its success status alone does not prove calendar coverage.

Explaining a gap does not authorize recovering it. Preserve frozen evidence and single-owner semantics. Do not recollect, fabricate digests, hand-mark a run complete, duplicate automation, or widen authorized source scopes. Resume or backfill only through the established generation contract after separate approval. When recovery would consume meaningful provider resources, present the bounded scope, work estimate, and feasible defer or existing-provider options before launching. Qualify any proposed local alternative separately; local inference is not automatically an equivalent or approved replacement.

Explaining a gap and recovering it are different completion states. Retain the exact unresolved dates and work estimates. A routine completion that moved the daily job forward does not fill historical holes.

## Review acceptance tests

1. A month with missing dates reports them and never describes partial weeks as complete.
2. A lesson already present in an existing skill is reinforced or corrected, not cloned.
3. A later project decision supersedes the earlier decision only within its stated scope.
4. A historical working artifact is marked demonstrated, not currently available or generally qualified without fresh tests.
5. An irrelevant recall result triggers targeted authority lookup, not a fabricated memory gap.
6. A successful scheduler response for an older date does not count toward the expected date.
7. Editing verification instructions does not turn a previously untested implementation into a production pass.
8. A saved weekly procedure does not imply a recurring job was created.
9. A recommendation and its implementation receipt retain separate dates and statuses.

These are review acceptance scenarios, not claims that documentation tests prove future agent behavior.

## Output pattern

Start with the useful result and exact coverage: requested range, timezone, week convention, unique validated dates, missing dates, rejected dates and reasons, and partial periods. Group the most consequential findings by week or theme, state which already exist, and name the smallest next action. Prefer a few evidence-backed changes over a quota of new skills, memories, or tools.

For each recommendation include:

- **Class and proposed action:** reinforce, reconcile, capture, retrieval repair, reuse, or investigate.
- **Dated evidence:** source date, section, evidence state, and uncertainty.
- **Existing guidance and gap:** actual skill sections or canonical records checked, including incomplete comparisons.
- **Authoritative destination:** the approved skill, project record, or memory location; identify any optional mirror separately.
- **Benefit and boundary:** expected benefit, required approval, privacy implications, and cost or exposure limits.
- **Verification:** the future acceptance test and current verification status; proposed tests are not completed tests.
- **Disposition:** recommendation only, approved, applied and verified, blocked, or pending; link a separately dated implementation receipt only if approved work actually occurred.

Finish with applied versus pending status. A recommendation-only review reports no applied changes.
